# Amarantha — Decision Log

Living log of architecture/tooling decisions and the empirical results that informed them. See `docs/project kickoff/initial claude code handoff.md` for the full RFC these decisions execute against.

## Session 1 — Vertical slice

- **Package manager: npm workspaces.** Only npm was installed (no pnpm/yarn); avoided adding new global tooling. Root `package.json` has `"workspaces": ["packages/*"]`.
- **Monorepo layout: `packages/core`, `packages/editor`, `packages/desktop` only.** `blocks`, `mdx`, `vscode` deliberately not stubbed — empty packages add workspace-graph noise with no payoff. `packages/mdx` is now being built out (Session 2, see below).
- **`Amarantha/` renamed to `packages/desktop`** via `git mv`, for consistency with the RFC's package table.
- **No build step for `@amarantha/core` / `@amarantha/editor`.** Raw TypeScript source, consumed directly by Vite via `resolve.alias` + `optimizeDeps.exclude` in `packages/desktop/vite.config.ts`.
- **MDXEditor (`@mdxeditor/editor@4.2.1`) is the v0 parse/serialize substrate**, per the RFC's explicit sanction. Confirmed React 19 peer-dep support before adopting (`peerDependencies: { react: ">=18 || >=19" }`). `@amarantha/core`'s public surface has zero MDXEditor/Lexical types.
- **Round-trip fidelity is NOT solved.** `packages/editor/src/roundtrip.smoke.test.tsx` asserts byte-identity on a trivial fixture (headings, bold/italic, link, a bullet list) and **fails**: MDXEditor's serializer normalizes list markers `-` → `*` even on this minimal input. This is the real, measured gap the RFC's Milestone 1 (custom source-preserving `DocumentEngine`) exists to close — not something papered over by weakening the test.
- **Revision fingerprint (`hashText`) is a placeholder**, not used for real conflict detection. `WriteRequest.baseRevision` is threaded through `desktopHost.writeDocument` but unchecked.
- **fs capability scope: `$HOME/**`**, chosen over unrestricted `**` (too broad) or a project-sandboxed scope (wrong model — Amarantha is a general file editor). Confirmed working via the Tauri v2 capability object syntax `{"identifier": "fs:allow-read-text-file", "allow": [{"path": "$HOME/**"}]}` against the actually-installed `tauri-plugin-fs@2.5.1` — no schema drift found.
- **No `toolbarPlugin`** in the MDXEditor plugin set — this is what yields the minimalist full-bleed canvas (MDXEditor has no built-in toolbar chrome unless that plugin is opted in).
- **Fork/upstream MDXEditor strategy for the base editor: not forked.** Used as an unmodified npm dependency for the core Rich/Source loop. (Superseded for the JSX/image editing surfaces — see Session 2.)
- **Known bug found and fixed during manual QA:** MDXEditor's `markdown` prop only seeds *initial* content — it does not react to prop changes after mount. Opening a new file updated `text` state but the already-mounted editor never displayed it. Fixed by keying `<AmaranthaEditor key={`${uri}:${mode}`}>` so React remounts the editor on file/mode change, forcing MDXEditor to re-seed from the new `markdown` value.

## Session 2 — Images, frontmatter, links, component registry

- **Images**: added `imagePlugin()` with host-supplied `imageUploadHandler`/`imagePreviewHandler` (both are real MDXEditor plugin options — confirmed against `node_modules/@mdxeditor/editor/dist/index.d.ts` before wiring, not guessed). `packages/desktop/src/lib/imageHost.ts` implements the desktop side:
  - Upload: pasted/dropped images are saved to an `assets/` folder next to the current document (created if missing) with a collision-resistant `<base36-timestamp>-<sanitized-name>` filename, and embedded as a relative `assets/<name>` markdown src. With no document saved yet (no directory to put `assets/` in), images are inlined as base64 `data:` URLs instead.
  - Preview/render: a relative or absolute local image src is resolved against the document's directory and converted via `@tauri-apps/api/core`'s `convertFileSrc` to a webview-renderable `asset://` URL; remote/data/asset URLs pass through untouched.
  - Enabling this requires the Tauri v2 asset protocol: `tauri.conf.json`'s `app.security.assetProtocol` set to `{"enable": true, "scope": ["$HOME/**"]}`. Enabling that setting caused Tauri's own build tooling to auto-add the `protocol-asset` Cargo feature to `tauri = { version = "2", features = [...] }` on the next `cargo build` — confirmed as expected/correct behavior, not a stray edit.
  - Added `fs:allow-write-file` and `fs:allow-mkdir` (scoped to `$HOME/**`) capability permissions alongside the existing text read/write/exists ones, for binary asset writes and `assets/` folder creation.
- **Frontmatter**: added `frontmatterPlugin()` — no host wiring needed, MDXEditor renders its own key/value frontmatter panel from `---`-delimited YAML at the top of the document.
- **Links**: `linkPlugin()` + `linkDialogPlugin()` were already enabled in Session 1; no changes needed this session, confirmed still working.
- **Testing convention adopted**: component tests select elements via `data-testid` (not text/role queries) — applied to the titlebar buttons (`open-button`, `save-button`, `mode-toggle-button`, `filename`, `dirty-dot`) and the editor surfaces (`amarantha-rich-editor`, `amarantha-source-view`).
- **Test infra gaps found and fixed** (both environment issues, not product bugs):
  - jsdom's `File`/`Blob` polyfill in the installed version doesn't implement `arrayBuffer()` — worked around in the test helper only (`packages/desktop/src/lib/imageHost.test.ts`'s `makeFile`), since the real Tauri webview's `File.arrayBuffer()` works correctly.
  - `@testing-library/react`'s automatic `afterEach(cleanup)` only self-registers when it detects a global `afterEach`, which Vitest doesn't provide unless `test.globals: true` is set — without it, DOM from one test leaked into the next within the same file. Set `globals: true` in both `packages/editor/vitest.config.ts` and `packages/desktop/vitest.config.ts`.
- **Component registry / JSX editing**: implemented `@amarantha/mdx` (new package: `createRegistry`, plus `personalWebsiteRegistry` — a temporary hardcoded registry for the QA target repo, standing in for the RFC's real per-repo `.amarantha/config` discovery, Milestone 3) and a Notion-style JSX props editor in `@amarantha/editor/src/jsx/`.
  - Extended `@amarantha/core`'s `ComponentDefinition`/`ComponentPropDefinition` (previously a bare stub) to the RFC's fuller shape: `kind: "flow"|"text"`, `props: Record<string, ComponentPropDefinition>` with `type: "string"|"number"|"boolean"|"enum"|"expression"`, `required`, `values` (enum), `description`.
  - Registry content grounded in a real survey of `/Users/franklinflitton/Git/Personal-Website/content` (35 files) rather than inferred from the renderer alone, per the RFC's explicit instruction — confirmed exact prop shapes for all 8 real JSX components (YouTube, IFrame, Img, Gist, NPM, Mermaid, UserJourney, UserJourneyMap) with verbatim usage examples. `pre`/`code`/`hr` from the renderer's component map override native markdown constructs, not literal JSX tags, so they're not registry entries.
  - **Judgment call, flagged rather than silently done**: the user asked to "hard-fork (copy the files)" MDXEditor's generic JSX editor. Before doing that, confirmed via `node_modules/@mdxeditor/editor/dist/index.d.ts` that every primitive a fork would need — `useMdastNodeUpdater`, `NestedLexicalEditor`, `MdastJsx`, `isMdastJsxNode`, `jsxPlugin`, `JsxComponentDescriptor` — is already a *public* export. Built `AmaranthaJsxEditor` as a new component composed from these public exports instead of literally copying MDXEditor's source: same end capability (full control over per-prop-type field rendering), without the upgrade-drift risk and duplicated-bugfix burden of a vendored copy whose internals (e.g. `useMdastNodeUpdater`) aren't even MDXEditor-internal — they're documented "Custom Editor Primitives" meant for exactly this. If a real limitation surfaces later that isn't reachable through public exports, revisit literal forking then.
  - `AmaranthaJsxEditor` renders one labeled field per declared prop — checkbox for boolean, `<select>` for enum, number input for number, monospace textarea for expression (covers Mermaid's multi-line `chart`, and UserJourney/UserJourneyMap's nested object/array props — these are JS object literals, not strict JSON, so edited as raw source text rather than a structured JSON editor; a real structured editor for that shape is future work), plain text otherwise. Commits via `useMdastNodeUpdater()` + a pure `buildAttributes` helper (`packages/editor/src/jsx/attributes.ts`, fully unit-tested) that preserves any attribute — including spread `{...expr}` attributes — not covered by the registry schema.
  - Unregistered components get a `"*"` catch-all descriptor (`UnknownJsxEditor`) per RFC's "unknown component stays source-preserved" requirement: renders a badge, calls no update hook, so the node round-trips unmodified. Known caveat, not yet manually verified: it doesn't visually render any children the unknown node may have (registered components today have none in practice, so this hasn't been exercised).
  - Verified end-to-end (not just typechecked) with a real MDXEditor mount + `jsxPlugin`: props editor renders with correct field values from parsed markdown, boolean bare-attributes round-trip, edited props re-serialize correctly, and a battery of tests using verbatim real content snippets (YouTube, Img with `framed`/`tall`, Gist, Mermaid's multi-line chart, UserJourneyMap's nested persona/expectations/phases) all render without crashing.
- **Still outstanding from this session's requests**: the image edit-toolbar base64⇄file conversion buttons. Research confirmed the seam: `imagePlugin`'s `EditImageToolbar` swap point plus `ImageNode.setSrc()` (also public) is sufficient — no image-plugin forking needed either. Not yet implemented.

## Session 3 — Native theming engine, `amarantha.config.json`, Tailwind Typography, fonts

Full design in `docs/theming-and-config-plan.md`. Implementation notes and judgment calls beyond that doc:

- **New `@amarantha/theme` package**: 10 themes (5 families × light/dark) as `[data-theme="<id>"]` CSS-variable blocks (`--am-bg/surface/border/text/text-muted/accent/accent-text`), plus two static "adapter" stylesheets — one mapping MDXEditor's own semantic vars (`--baseBg`, `--accentSolid`, `--admonition*`, ...) onto `--am-*`, one doing the same for Tailwind Typography's `--tw-prose-*` vars. Confirmed against the real shipped `@mdxeditor/editor` stylesheet that a single `.amarantha-app .mdxeditor { ... }` rule (specificity 0,2,0) reliably overrides MDXEditor's own class-based light/dark rule (0,1,0) regardless of import order — verified in the actual `vite build` output, not just by inspecting source.
- **`resolveComponentRegistry(uri)` → `resolveWorkspaceConfig(uri)`** on `EditorHost`: real `amarantha.config.json` discovery (`@amarantha/core`'s `discoverWorkspaceConfig` + `mergeComponentDefinitions`) replaces the RFC's placeholder `.amarantha/config` naming and retires `personalWebsiteRegistry` as `desktopHost`'s hardcoded fallback (Milestone 3, closed). `personalWebsiteComponents.ts`/`personalWebsiteRegistry` are kept as-is in `@amarantha/mdx` — they're still exercised by existing tests as real-content fixtures, just no longer wired as the app's default registry.
- **Theme mode (light/dark/system) and palette family are independent preferences**, not one flat theme id — added mid-session at the user's request so a repo's palette opinion (`amarantha.config.json`'s `theme: ThemeFamily` field) never overrides the user's own light/dark/system choice. `AmaranthaConfig.theme` is typed as `ThemeFamily`, never a full `ThemeId`.
- **Tailwind v4 + `@tailwindcss/vite` + `@tailwindcss/typography`**, scoped to `packages/desktop` only (the only package with a Vite build) — `packages/core`/`mdx`/`editor`/`theme` stay build-tool-agnostic. `AmaranthaEditor`'s prose classname (`proseClassName`, default `"amarantha-prose prose"`) and size (`proseSize`, via a static `Record<ProseSize, string>` lookup — not a template literal, which Tailwind's content scanner wouldn't detect) are now props, not hardcoded, as the seam for a future non-Tailwind design system.
- **Fonts**: Geist Sans/Mono (`@fontsource-variable/geist`, `@fontsource-variable/geist-mono`) are the only vendored font packages — bundled as the default, no network needed. Any other font is fetched on demand from the Fontsource API (`api.fontsource.org` for metadata, `cdn.jsdelivr.net/fontsource` for the actual woff2, confirmed against the live API before coding — schema is `variants[weight][style][subset].url.woff2`) and cached to `$APPDATA/fonts/<id>/` via the same Tauri fs pattern `imageHost.ts` already uses for local images, exposed through `packages/desktop/src/lib/fontHost.ts`. **Judgment call, flagged**: the user asked for "any font from Fontsource" (2096 entries via `api.fontsource.org/v1/fonts`); rather than fetching/caching that whole catalog for a searchable combobox, shipped a ~9-font curated shortlist (`@amarantha/theme`'s `CURATED_FONTS`) plus a free-text "custom Fontsource ID" field that hits the exact same fetch/cache path — confirmed with the user mid-session before building it this way. A third free-text "system font" option sets `font-family` directly with no fetch/cache at all.
- **New Tauri capability/config surface**: `$APPDATA/**` added alongside the existing `$HOME/**` scope on all fs permissions and the asset-protocol scope (font cache lives under `$APPDATA/fonts/`, outside the `$HOME`-scoped document/image paths the original scope was sized for). `tauri.conf.json`'s CSP is already `null` (from Session 1), so the new `fetch()` calls to the Fontsource API/CDN needed no CSP change.
- **Verification performed**: `npm run typecheck` clean across all 5 workspaces; `npm test` clean except the pre-existing, already-documented `roundtrip.smoke.test.tsx` list-marker failure (Session 1, unrelated); a real `vite build` inspected byte-for-byte for all 10 `data-theme` blocks, `prose-sm/base/lg/xl/2xl`, `Geist Variable`/`Geist Mono Variable`, `--tw-prose-body`, and `--baseBg` in the emitted CSS. Not yet done: an actual visual pass in the running app (all 10 themes × the font/size pickers) — the plan's verification checklist items 1–4 and the Fontsource network fetch path are unexercised beyond the build-time checks above.
